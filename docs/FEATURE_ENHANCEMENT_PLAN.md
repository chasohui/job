# 기능 고도화 계획

> **작성 일자:** 2026-08-30
> **배경:** [FEATURE_ENHANCEMENT_PROGRESS.md](./FEATURE_ENHANCEMENT_PROGRESS.md)에서 PRD 5.8(직무 무관 결과 판정)을 실제 구현한 뒤 남겨둔 후보 목록을, 우선순위·구현 난도·PRD 범위 제약을 기준으로 정식 계획으로 재구성한 문서.
> **전제:** [PRD.md](../PRD.md) 6장의 범위 제한(로그인/결제/DB 저장/외부 서비스 연동 없음)은 별도 합의 없이는 계속 준수한다. 이 전제를 벗어나는 항목은 Phase D로 분리해 별도 결정을 받는다.

## 우선순위 기준

- **Impact**: 사용자가 실제로 체감하는 가치(핵심 가치인 "정확한 AI 분석 + 실행 가능한 순서" 강화 여부)
- **Effort**: 구현 난도 (클라이언트 전용 < AI 프롬프트/로직 < 인프라 신규 도입)
- **Risk**: PRD 범위 제한과 충돌하는지 여부 — 충돌 시 임의로 진행하지 않고 별도 확인 필요

---

## Phase A — Quick wins (클라이언트 전용, 인프라 변경 없음)

우선순위 1순위. 기존 아키텍처(로그인/DB 없는 순수 클라이언트+API route) 안에서 바로 구현 가능.

| 항목 | 내용 | Impact | Effort |
|---|---|---|---|
| **Mock 폴백 도메인 확장** | `lib/mock-analysis.ts`가 현재 프론트엔드/백엔드/데이터 3개 직무군만 커버함. `GEMINI_API_KEY` 미설정 환경이나 API 장애 시 폴백 품질이 직무에 따라 크게 떨어짐. 기획/마케팅/디자인/영업/HR 등 5개 내외 도메인 추가 | 중 (폴백 품질 균일화) | 낮음 |
| **결과 내보내기** | 결과 화면에 "복사하기"(마크다운/텍스트로 클립보드 복사) + 인쇄용 CSS(`@media print`) 추가. 서버 저장 없이 순수 클라이언트 기능이라 PRD 범위와 완전히 부합 | 높음 (사용자가 결과를 실제로 들고 나갈 수 있게 됨 — PRD 목표 "무엇을 준비해야 하는지"의 활용성 직결) | 낮음 |
| **단계별 체크리스트 인터랙션** | 1~3단계 추천 항목 카드에 체크박스 추가, `localStorage`에 완료 상태 저장(입력값이 아닌 UI 상태이므로 PRD 4.6 "DB 저장 없음"과 무관). 새로고침해도 체크 상태 유지 | 중 (진행감 제공) | 낮음 |

**권장 착수 순서:** 결과 내보내기 → Mock 도메인 확장 → 체크리스트. 내보내기가 사용자 체감 가치가 가장 크고, 나머지 둘은 서로 독립적이라 병렬 진행 가능.

## Phase B — 클라이언트 상태 고도화 (localStorage 활용)

Phase A보다 UX 설계가 더 필요하지만 여전히 인프라 추가 없이 가능.

| 항목 | 내용 | Impact | Effort | 비고 |
|---|---|---|---|---|
| **이전 분석 이어보기** | 마지막 입력값+결과를 `localStorage`에 저장, `/start` 재방문 시 "이전 분석 불러오기" 옵션 제공 | 중 (재방문 이탈 방지) | 중 | PRD 4.6은 "DB 저장 없음"만 명시 — 브라우저 로컬 저장은 범위 밖 항목이 아님. 다만 오래된 결과를 새 결과로 오인하지 않도록 UI 문구 필요 |
| **역량/단계별 후속 질문** | 각 핵심 역량/준비 항목 카드에 "더 자세히 알고 싶어요" 버튼 → 기존 컨텍스트(직무, 준비 상황, 해당 항목)를 포함해 Gemini에 짧은 재질의 후 카드 내 확장 표시 | 높음 (PRD 사용자 스토리 4 "바로 행동하기"를 한 단계 더 깊게 지원) | 중~높음 | Gemini 호출이 늘어나므로 `lib/rate-limit.ts` 한도(분당 10회)와 비용에 영향 — 별도 rate limit 트랙 필요할 수 있음 |
| **결과 공유 이미지** | 핵심 역량/1단계 요약을 canvas로 렌더링해 이미지 다운로드(서버 저장 없이 클라이언트에서 생성) | 낮음~중 (바이럴 유입 채널) | 중 | Phase A 내보내기 이후 우선순위 재검토 |

---

## Phase C — AI 품질/정확도 고도화

기능 추가가 아니라 기존 핵심 기능(AI 분석 정확도)의 완성도를 높이는 트랙. PRD 완료 조건에는 이미 포함돼 있지만 지속 개선 여지가 있음.

| 항목 | 내용 | Impact | Effort |
|---|---|---|---|
| **`checkRelevance` 비용 최적화** | 현재 관련성 재판정이 매 요청 추가 Gemini 호출(최악 4회/요청)을 유발. 생성 프롬프트 자체에 관련성 기준을 강화해 1차 통과율을 높이고, 재판정은 저비용 모델로 분리하는 방향 검토 | 중 (비용 절감, 응답 지연 감소) | 중 |
| **모델 업그레이드 검토** | `HARDENING_PROGRESS.md`에 이미 기록된 `gemini-3.7-flash` 후보 — 품질/속도 비교 후 전환 여부 결정 | 중 | 낮음 (비교 실험 자체는 낮음, 전환 후 회귀 테스트 필요) |
| **직무별 프롬프트 보강(few-shot)** | 비주류 직무(예: 특수 전공×희망 직무 조합)에서 결과 품질 편차가 있는지 실제 로그/피드백 기반으로 점검 후 프롬프트에 예시 추가 | 중 | 중 |

---

## Phase D — 인프라 결정 필요 (PRD 범위 제한과 충돌)

**아래 항목은 PRD 6장 "범위 제한" 조건과 직접 충돌하므로, 임의로 진행하지 않고 먼저 PRD 개정 여부를 사용자와 확인해야 함.**

| 항목 | 충돌하는 PRD 조항 | 필요 인프라 |
|---|---|---|
| 영구 공유 링크 | "사용자 입력 및 결과 DB 저장 없음" | KV/DB (Vercel Marketplace: Neon/Upstash 등) |
| 이메일 발송 | "외부 서비스 연동 없음" | 이메일 서비스 연동 |
| 계정 기반 히스토리 | "로그인/회원가입 없음", "DB 저장 없음" | 인증 + DB |
| Rate limit 공유 스토어 전환 | (PRD 충돌 아님, `HARDENING_PROGRESS.md` P1에서 이미 보류됨) | Upstash Redis 등 |

이 트랙은 "서비스를 1회성 분석 도구에서 지속 사용 도구로 전환할지"에 대한 제품 방향 결정이 선행되어야 하므로, Phase A~C와는 별도로 사용자 확인 후 착수.

## 권장 다음 액션

1. **Phase A 3개 항목**부터 순차 구현 (인프라 변경 없이 바로 착수 가능, 리스크 최소)
2. Phase A 완료 후 Phase B(이어보기 / 후속 질문)와 Phase C(AI 품질) 중 어느 쪽을 우선할지 재확인 — 전자는 UX 확장, 후자는 핵심 품질 강화로 성격이 다름
